PRAPOGATION -----  (if any failure then rather than keep unused data just rollback everything it means prapogation)
prapogation defines how the transactions are managed when method is invoked by another transaction.(if we are callling one transaction inside another transaction in this scenario prapogation is useful.
example --- suppose we have two methods M1 AND M2 and both the methods implemented transactional suppose we are invoking M2 from M1.
            and suppose m2 transaction is failed how we want m1 transaction is continued. --------------
			1. @Transactional(prapogation = Prapogation.REQUIRED)
			Propagation.REQUIRED means the method will join an existing active transaction if one exists; otherwise, Spring will create a new transaction.
			All participating methods share the same transaction, so a failure in any method causes a rollback of the entire transaction.

ISOLATION --
   in transaction isolation controls the visibility changes made by one transaction into other transaction.
   if there is two transaction T1 and T2 what T1 is doing it should update to T2 this is the roll of isolation to make the data consistency between multiple transaction.
   THE isolation uses default REPEATABLE_READ that we can change.
   
   public enum Isolation{
     DEFAULT,
	 READ_UNCOMMITED,
	 READ_COMMITED,
	 REPEATABLE_READ,
	 SERIALIZABLE);
	 
	1. READ_UNCOMMITED --  it means dirty read
	suppose two transaction M1 and M2
	there is table columns ID, NAME, PRICE, STOCK
	M1 transaction is doing stock update and M2 is reading stock value of that same product.
	suppose the stock value is 10 and M2 also reading 10 it means M2 is reading uncommited data ,suppose in future M1 is rollback the change suppose 20 but still M1 getting 10 it means data is not consistency between two transaction.
	
	then if we use trasaction level isolation read_uncommited,then what m1 is doing that uncommited value also read by M2.
	EXAMPLE --------------

		 public void testReadUncommitted(int id) throws InterruptedException {

        // Start Transaction A (Thread 1) to update the stock but not commit, then roll back
        Thread threadA = new Thread(() -> {
            try {
                productService.updateStock(id, 5);  // Change stock to 5
            } catch (InterruptedException e) {
                e.printStackTrace();
            }
        });

        // Start Transaction B (Thread 2) to read the stock
        Thread threadB = new Thread(() -> {
            try {
                Thread.sleep(2000);  // Wait a moment to ensure Thread A starts and holds the transaction
                int stock = productService.checkStock(id);  // Read stock during Transaction A
                System.out.println("Stock read by Transaction B: " + stock);
            } catch (InterruptedException e) {
                throw new RuntimeException(e);
            }
        });

        // Start the threads
        threadA.start();
        threadB.start();

        // Wait for threads to complete
        threadA.join();
        threadB.join();
			}
		}

		6.
		@Transactional(Isolation = isolation.SERIALIZABLE)
		..ensure that transactions are executable in manner to running them sequantially one after another even they are executing concurrently.
		Example -----
		there are two transaction M1 and M2 
		M1 is updating the value and M2 is reading the value once M1 is started at the same time if you star the M2 transaction even though both are executing concurrently it will apply the lock
		serializable isolation apply the lock. first M1 should complete the task then get chance M2 transaction for execution there will be no concurrent execution. one after another.
		“Isolation.SERIALIZABLE is the strictest isolation level.
			It guarantees that concurrent transactions produce the same result as if they were executed sequentially.
			The database enforces this using locks, so if one transaction is modifying data, other transactions accessing the same data will wait until it completes.”
